# Gate validity

Read `SKILL.md` first. This file covers gates that pass while no longer being in
a position to answer.

## Independent sources

A gate is informative only when checker and checked do not derive from the same
source.

Examples of uninformative agreement:

- a generated index compared with the headings that generated it;
- a measured value compared with a ceiling copied from that value;
- a test of configured counts that parses the command string declaring them;
- a freshness check comparing two synchronized copies of the same false claim.

Ask:

1. What would have to break for this to go red?
2. Where does each side of the comparison come from?
3. Who chose both sides?
4. Could the subject and its expected inventory disappear together?

Completeness needs an independent denominator: an expected manifest, an external
source, or a mutation that removes a known required subject.

## Premises are checked every run

A test double can stop intercepting the production seam after a refactor. The
request then fails immediately, the condition needed to expose the bug never
exists, and the gate passes faster.

Assert the premise before the verdict:

- the stub matched at least once;
- the selected test count is non-zero;
- the fixture contains every requested component;
- the delayed or concurrent state was actually reached;
- the external service or job that permits a local skip really executed.

> **A check whose input disappeared must not report success faster than before.**

## Mutation protocol

1. Start from a green unmutated baseline.
2. Use a disposable clean copy.
3. Count or identify the mutation target before editing.
4. Apply one minimal mutation.
5. Independently assert that the intended property changed.
6. Run the untouched gate.
7. Require the specific check to fail while unrelated checks remain green.
8. Restore, hash-compare, and inspect status.

A mutation that fails everything proves the subject was broken, not that the
gate distinguishes the behavior. A mutation that stays green may mean the gate
missed or the mutation did not apply.

Run the mutation after final comments, fixtures, and refactors. "Watched failing"
has a timestamp.

## Coverage is measured by deletion

Grepping tests for a rule's words reimplements the matching rule and cannot show
whether deleting the rule would matter.

For prose or configuration gates:

1. define the rule population and publish the selection predicate;
2. start green;
3. delete one rule at a time from a disposable copy;
4. run the gates;
5. count a rule held only when its deletion causes a relevant failure.

A hand-written manifest also needs a count assertion against the section it
claims to cover, or new rules arrive unenrolled while coverage remains perfect.

Some required content cannot be gated generally because legitimate deletion is
routine. Use fixed-string spot checks for a small set of load-bearing phrases
and independent review for the rest.

## Fail closed under uncertainty

Missing input, unreadable directories, malformed locks, unknown process results,
and empty censuses are not permissive values.

Use distinct output states:

- measured and within policy;
- measured and close to policy;
- refused by policy;
- unreadable or incomplete, therefore refused.

Over-counting may conservatively refuse. Any observation that can under-count
must refuse the whole safety decision.

Prove completion by presence: enough completed observations **and** no pending
ones. Absence of a bad token passes on empty input.

## Green baseline before a sweep

A mutation sweep started from a red baseline reports every mutation "caught",
because every run has a failure to point at.

Refuse to begin unless the unmutated baseline is green. Print any existing
failure and stop.

## Baseline provenance

Fixtures or snapshots generated by the code they test share a source. Inspect
them when adopted, and record which independent property makes them correct.

A baseline is evidence about drift from its origin, not evidence the origin was
good.

## State the mechanism and cost

A guard's documentation names:

- what it executes;
- what it does not execute;
- what it reads and writes;
- its expected cost;
- which operations bypass it.

Explaining only the hazard teaches why the guard exists and leaves readers to
invent what it does. A silent-on-success guard has an audience consisting mostly
of people it already stopped, so its refusal output must carry the mechanism too.
